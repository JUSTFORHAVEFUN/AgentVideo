XMLVideoEditor Technical Stack and Performance Analysis
Version 1.6.0-gpu2d

---

OVERVIEW

XMLVideoEditor is a GPU-accelerated video renderer that turns a single XML
file into an MP4. It runs on Android via Termux with no window system, no
desktop compositor, and no proprietary codecs. Every component is written in
Python and drives the GPU through standard Khronos APIs.

Typical performance on an 8-core Android phone:

  56-second 1080p video with mixed 2D text and 3D scenes
  ~21 seconds wall time (2.7x realtime)
  ~0.5 MB output file with H.264 CRF23

The same project rendered through cairo (CPU fallback) takes over 300 seconds.
That is a 15x speedup, not a minor optimization.

3D Rendering

  No external 3D library dependency

RENDERING PIPELINE

Frame construction goes through four stages:

  1. XML parse - builds an in-memory project graph
  2. Frame evaluation - resolves keyframes and expressions per timestamp
  3. Rasterization - draws 2D primitives or 3D meshes onto a GPU framebuffer
  4. Encoding - pipes RGBA pixels to ffmpeg via stdin, H.264 out

For 2D content, an intermediate SVG string can be generated and parsed.
For 3D scenes, mesh instances are drawn directly with matrix transforms.

---

WHY IT IS FAST

1. Offscreen GPU rendering with no compositor

  EGL pbuffer surfaces bypass the Android window system entirely.
  There is no Activity, no SurfaceFlinger, no vsync. Frames are rendered
  to a framebuffer object and read back with a single glReadPixels call.
  The whole loop runs inside a single Python process.

2. Persistent GPU context per thread

  Raster2D and GL3D objects are created once and cached per thread. Shader
  programs, vertex buffer objects, framebuffer objects, and texture atlases
  all survive across frames. Setting up a new context costs around 4 ms and
  happens exactly once per worker process.

3. Text rendered as bitmaps, not glyph quads

  Each unique combination of text, font, size, and weight is rendered once
  into a Pillow bitmap and cached. Subsequent frames upload the same texture
  and issue a single quad draw. Text rendering drops from per-frame glyph
  layout to a dictionary lookup.

4. Vertex shader deformation

  Wave, flag, and curl animations run entirely on the GPU. The CPU sends
  only four floats per frame (amplitude, frequency, speed, time). A 64x64
  mesh with thousands of vertices costs nothing to animate because the
  vertex shader does all the work.

5. Multi-light shading in a single draw call

  Up to 8 lights of 4 types (ambient, directional, point, spot) are passed
  as uniform arrays. The fragment shader loops over them. A scene with 3
  lights and 50 meshes still issues 50 draw calls, not 150.

6. Static segment deduplication

  The renderer hashes each frame's evaluated properties. When consecutive
  frames share identical hashes, the first one is rendered and the rest are
  hard-linked. In typical presentation videos 60 to 70 percent of frames
  are duplicates. This single optimization cuts render time by half.

7. Three-process pipeline parallel rendering

  The timeline is split into chunks of at most 12 seconds. Each chunk goes
  to an independent Python process with its own EGL context, its own GPU
  state, and its own ffmpeg encoder. Measured on 8-core hardware, 3 processes
  is optimal: below that the encoders serialize, above that GPU and IO
  contention eats the gains.

8. ffmpeg ultrafast preset for intermediate chunks

  Every chunk is encoded with libx264 ultrafast at CRF16. Quality does not
  matter for the intermediate file because the final merge re-encodes
  everything at medium CRF23. Ultrafast is roughly 8 times faster than medium
  at the cost of 3 to 4 times the file size, and the file only lives on disk
  for a few seconds.

9. Audio mixing deferred to the end

  Video chunks are rendered with no audio track at all. The final concat
  produces a silent video, then a single ffmpeg pass overlays every audio
  clip with proper delays, fades, and volumes. This removes AAC encoding
  from the parallel path entirely.

10. Cairo fallback only when needed

  SVG features that the GPU path does not support (masks, gradients, filters)
  are detected at parse time. The renderer routes only those specific frames
  to cairo, leaving everything else on the fast path.

11. Zero-copy readback

  glReadPixels writes directly into a preallocated ctypes buffer. The buffer
  is reshaped into a NumPy array with a view, not a copy. From there the data
  goes straight to ffmpeg stdin as bytes.

12. Memory layout alignment

  Vertex data uses a single interleaved 32-byte stride: position (2 floats),
  UV (2 floats), color (4 floats). One buffer upload, one attribute pointer
  setup, one draw call. No per-attribute buffer switching.

13. Optional fastpath with GPU instancing

  When <space3d fastpath="1"> is set, the renderer scans every static mesh
  and groups them by (type, texture, color). A group of 16 or more identical
  shapes becomes a single glDrawArraysInstanced call with per-instance model
  matrices stored in a VBO.

  Measured effect on a 1200-building city scene at 1280x720:
    Draw calls per frame:   1200  ->  5
    GPU frame time:         90ms  ->  12ms

  Trade-off: instancing transforms the normal vector with mat3(M) directly
  instead of the correct inverse-transpose. Under non-uniform scale (a cube
  stretched into a tall building), the lighting flattens: a building that
  should show three distinct lit faces renders as a single flat color.

  Because this matters for the flagship case (a night city skyline), the
  fastpath is off by default. Users who want the extra speed turn it on per
  scene, accepting the visual simplification. A correct inverse-transpose
  normal transform is possible but costs an extra mat3 inversion per vertex,
  which on mobile GPUs can cost more than the draw call savings.

PERFORMANCE BREAKDOWN

Per-frame cost in the fast path, measured on a mid-range Android device:

  EGL begin and clear             0.3 ms
  Vertex buffer upload            0.1 ms
  Draw calls                      0.5 to 2.5 ms
  glFinish and glReadPixels       3.5 ms
  PNG encode, compress_level=1    0.5 ms
  ffmpeg H.264 ultrafast          8 to 25 ms (depends on scene)

The readback and encode dominate. The actual drawing is nearly free.

Scene-level performance, 3D flag scene at 1280x720:

  180 frames including camera motion and 50+ meshes
  4.5 seconds total, of which GPU rendering is 0.9 seconds
  The remaining 3.6 seconds are H.264 encoding overhead

COMPARISON WITH CPU PATH

Same 56-second project rendered through cairo:

  CPU cairo path:    over 300 seconds
  GPU fast path:     under 40 seconds
  Combined with aggressive pipeline: under 25 seconds

The GPU path is not just faster per frame. It is also more correct:
font fallback for CJK characters, synthetic bold for missing weights, and
proper subpixel positioning are all handled natively.

---

FASTPATH: WHEN AND WHY

The fastpath is an opt-in GPU instancing mode. It exists because the two
costs it eliminates -- draw call submission and per-mesh CPU transforms --
dominate the profile on scenes with hundreds or thousands of small static
objects. A city skyline at 1280x720 with 1200 buildings spends more time
in Python transform loops than the GPU spends rasterizing.

Three rules govern when it helps:

  · Many identical shapes: two or more mesh entries with the same type,
    texture, and color. Buildings of four city textures group into four
    instanced draws.

  · Small on screen: if the objects cover less than a few pixels each,
    the flat-lighting artifact is invisible.

  · Static: meshes with animations, deform attributes, or per-instance
    colors are excluded -- they cannot share a single model matrix buffer.

The fastpath is not applied to parametric instances (meshes that use $var
substitution). Parametric instances always run: they are a feature, not an
optimization, and turning them off would remove user-authored content.

The final trade-off is a productivity question, not a technical one. The
correct path costs about 20 percent more wall time on a 16-second video
(36 seconds vs 29 seconds on an 8-core phone). That is not a large penalty,
which is why the default is correct-by-default and the fastpath is the
opt-in exception.

DESIGN PHILOSOPHY

The project makes three deliberate choices that shape everything else.

First: there is no intermediate file format. The renderer produces RGBA
bytes in memory and hands them to ffmpeg over a pipe. Nothing touches the
disk except the final encoded chunks.

Second: the GPU is treated as a single shared resource. Parallelism happens
at the process level, not the thread level. Each worker owns its own context
and its own encoder. There is no locking, no queue, no shared state.

Third: anything that can be cached is cached. Shader programs, vertex
buffers, glyph atlases, texture uploads, parsed XML, frame hashes. The
system trades memory for speed at every opportunity because the target
device has plenty of both.

FINAL NOTE

The speed comes from removal, not addition. No window, no compositor, no
intermediate format, no per-frame layout, no per-frame context setup, no
per-frame audio encoding. Every layer that could be removed was removed.
What is left is a tight loop that pushes pixels from a GPU framebuffer into
an H.264 encoder with as few steps as possible in between.
